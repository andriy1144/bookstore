# Архітектура компонентів проєкту "BookStore"

Цей документ описує структуру клієнтського застосунку, розподіл відповідальності між компонентами, їхні контракти та керування станом (згідно з етапами розробки ЛР 1.2 — ЛР 3.2).

## 1. Ієрархія маршрутів та компонентів

Дерево відображає вкладеність компонентів, маршрутизацію (React Router) та області дії провайдерів стану:

App (Точка входу, Routes)
 └── AppLayout (Спільна оболонка)
      ├── SiteHeader (Шапка)
      │    └── MainNav (Навігація)
      └── BookSelectionProvider (Context API: глобальний стан вибору книги)
           └── OrdersProvider (Context API: колекція замовлень, асинхронні стани)
                ├── / -> HomePage
                ├── /books -> CatalogContainer -> BookListPage
                │    ├── BookFilters (Керовані поля)
                │    └── BookList -> BookCard -> AvailabilityBadge
                ├── /books/:bookId -> BookDetailsPage
                └── /orders -> OrdersLayout (Вкладене компонування + OrderNotice)
                     ├── /orders -> OrdersPage (Список з фільтрацією та сортуванням)
                     ├── /orders/new -> OrderCreatePage (Керує станом `draft` та `isSubmitting`)
                     │    ├── OrderForm (Спільна керована форма)
                     │    └── OrderSummary
                     ├── /orders/:orderId -> OrderViewPage (Перегляд та видалення)
                     └── /orders/:orderId/edit -> OrderEditPage (Редагування існуючого запису)

## 2. Патерн "Адаптер" та шар даних

Для ізоляції UI-компонентів від логіки роботи з сервером реалізовано шар доступу до даних:
*   `mockStorage.js`: Імітує базу даних за допомогою `localStorage` та створює штучні мережеві затримки (Promise delays) для імітації асинхронності.
*   `api.js` (Адаптер): Єдина точка входу для React-компонентів. Надає методи `getBooks`, `getOrders`, `createOrder`, `updateOrder`, `deleteOrder`. У майбутньому `mockStorage` може бути замінений на реальні `fetch`-запити без зміни коду компонентів.
*   `orderValidation.js`: Чиста функція `validateOrder()`, що ізолює предметні правила валідації та нормалізації даних від UI.

## 3. Контракти ключових компонентів (Props)

| Компонент | Вхідні властивості (Props) | Домовленість / Відповідальність |
| :--- | :--- | :--- |
| **AppLayout** | `title`, `links`, `children` | Створює спільну оболонку з шапкою, `main` та підвалом. |
| **BookList** | `books`, `selectedId`, `onSelect` | Відповідає за мапінг масиву та обробку порожнього стану каталогу. |
| **OrderForm** | `bookTitle`, `draft`, `errors`, `isSubmitting`, + callbacks | Спільна керована форма для створення та редагування. Відображає дані та помилки, блокується при `isSubmitting`. Без власного стану. |
| **FormField** | `id`, `label`, `hint`, `error`, `children` | Обгортка для полів вводу. Відображає текст помилки (`error`), якщо він переданий. |
| **AppButton** | `type`, `variant`, `disabled`, `children` | Універсальна кнопка. `variant` визначає стилістику Bootstrap. |

## 4. Карта стану застосунку

| Значення / Стан | Призначення | Власник стану | Споживачі | Дія скидання / Оновлення |
| :--- | :--- | :--- | :--- | :--- |
| `orders` (масив) | Колекція збережених замовлень | `OrdersProvider` | `OrdersPage`, `OrderViewPage`, `OrderEditPage` | Оновлюється асинхронно через CRUD-методи Провайдера. |
| `isLoading`, `error` | Стани асинхронних запитів | `OrdersProvider` | Всі сторінки розділу `/orders` | Скидається при успішному `fetchOrders()`. |
| `query`, `sortBy` | Фільтрація та сортування списку | URL (`useSearchParams`) | `OrdersPage` | Кнопка очищення / Зміна URL. |
| `draft` (чернетка) | Дані вводу форми | `OrderCreatePage`, `OrderEditPage` | `OrderForm`, `OrderSummary` | Демонтування сторінки / Успішне збереження. |
| `errors` (об'єкт) | Помилки валідації форми | `OrderCreatePage`, `OrderEditPage` | `OrderForm` | Скидається при зміні відповідного поля. |
| `isSubmitting` | Блокування форми при відправці | `OrderCreatePage`, `OrderEditPage` | `OrderForm` | Скидається після завершення Promise запиту. |

## 5. Обґрунтування архітектурних рішень

1. **Context API для колекції (`OrdersProvider`):**
   Провайдер інкапсулює масив замовлень та асинхронні методи роботи з ним. Завдяки цьому стан замовлень не втрачається при навігації між сторінками, а будь-яка сторінка розділу (Створення, Редагування, Список) має доступ до єдиного джерела правди.
2. **Патерн "Адаптер" (`api.js` та `mockStorage.js`):**
   Відокремлює UI від логіки запитів. Дозволяє імітувати затримки та мережеві помилки (`ApiError`) без засмічення компонентів специфікою `localStorage`.
3. **Повторне використання `OrderForm`:**
   Форма винесена в окремий stateless-компонент, який лише приймає `draft` і колбеки. Це дозволило використати одну й ту саму розмітку та логіку відображення помилок як для `OrderCreatePage`, так і для `OrderEditPage`.
4. **Параметри фільтрації у URL:**
   Стан пошуку (`query`) та сортування (`sortBy`) у списку замовлень перенесено до параметрів URL (через `useSearchParams`). Це гарантує, що при перезавантаженні сторінки або копіюванні посилання результати фільтрації відновлюються.
5. **Розподіл життєвого циклу стану:**
   Чернетка форми (`draft`) навмисно залишена локальною (`useState` у сторінковому компоненті). Вона живе лише поки відкрита сторінка створення/редагування, і знищується при переході, що запобігає випадковому збереженню небажаних даних. Водночас колекція `orders` живе глобально в Провайдері.
